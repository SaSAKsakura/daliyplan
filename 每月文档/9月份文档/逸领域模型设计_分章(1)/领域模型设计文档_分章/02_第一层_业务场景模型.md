## 2. 第一层：业务场景模型


> **第一层：业务场景模型**（建模第一阶段）：**先按场景分析业务逻辑**——产品 → 主题域 → 场景 → 子场景 → 子场景活动（2.1～2.5），由子场景活动分析识别**业务对象**与**业务行为**；识别的业务对象经 `cdm_aggregate_scenario`（3.13）衔接**第二层概念数据模型**（第 3 章），识别的业务行为登记为业务事件/事件处理器/业务服务（2.6～2.8）。**域归属**：本章 8 张表均属**研发固化域**（`ddd`），由配置系统写入维护。

> **前缀约定（重要）**：本章 7 张业务场景表（`prod_subject`/`prod_scenario`/`prod_subscenario`/`prod_activity`/`prod_event`/`prod_eventhandler`/`prod_service`）与第五层产品服务模型（§6）**共用 `prod_` 前缀**。两条必须记住的约定：
>
> 1. **前缀不是层次标识**。业务场景层（第一层）与产品服务层（第五层）物理表名同为 `prod_` 前缀，**不应从前缀判断建模层次**；层次归属由 §11 表清单的「层级」列与本文件的章节归属表达。
> 2. **资产性质以前缀之外的标准判断**。本章 7 张表属**建模资产**（研发固化域 `ddd`）——`prod_` 前缀下共 22 张表 = 建模资产 7 张（本章）+ 产品交付物 15 张（含 `prod_product`，见 2.1 / §6）。总口径：建模资产 28 + 产品交付物 22 = 50 张（**产品交付物 20→22 由新增配置策略两张表所致**）（另 `app` 域 19 张，全模型合计 **69 张**）。
>
> 另 **`prod_product` 亦保留在本章**（2.1），因其是**建模入口与追溯链顶端**——产品属**产品交付物**（研发固化、跨客户复用），但作为建模起点的定义就近放在本章。
> **schema 表示"研发侧/客户侧"，与表名前缀是两个独立维度**——两层的 `prod_` 表均位于 `ddd` schema 内（见 1.5 节）。

### 2.1 prod_product — 产品/子系统定义（业务场景层·产品交付物）

> 定义**产品/子系统**（Product / Subsystem），是业务领域建模的**顶层组织单元**与**业务场景层入口**。产品回答"系统解决什么业务问题、边界如何划分"——业务场景分析与业务对象建模均在产品的业务范围内开展，形成"产品 → 主题域 → 场景 → 业务对象 → 物理表"的追溯闭环。
> 产品既是**建模的业务边界入口**，也是**交付单元**（应用系统按产品组合启用，见 8.2）。产品与子系统是同一建模入口，层级关系由「产品 → 主题域 → 场景」链路表达，无需再用类型字典区分；层级归属通过 `prod_subject.product_id`（见 2.2）自下而上收敛。

| 字段 | 类型 | 约束 | 说明 |

| `row_uuid` | uuid | UN, NOT NULL | 全局行标识（UUID v4） |
| `product_code` | varchar(64) | UN, NOT NULL | 产品/子系统编码 |
| `product_name` | varchar(128) | NOT NULL | 产品/子系统名称 |
| `description_txt` | text | | 业务描述（解决什么问题、业务范围） |
| `owner_user_id` | integer | | 业务负责人（app.user_id，`_by` 操作人后缀） |
| `cdm_status_dict` | varchar(64) | NOT NULL, DEFAULT 'ACTIVE' | 状态（字典）：`ACTIVE`/`INACTIVE`/`ARCHIVED`。`_dict` 字典引用 |
| `sort_order` | integer | | 排序 |
| `create_by` | integer | NOT NULL | 创建人（app.user_id） |
| `create_ts` | timestamp | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 创建时间 |

### 2.2 prod_subject — 主题域定义（业务场景层）

> **主题域（Subject Area）**：按业务域（采购、销售、库存、组织、财务等）对业务场景与聚合/实体进行分组管理，支撑**领域导航、实体检索与权限分级**。主题域挂在产品/子系统（`prod_product`）下，是概念层的"业务分类骨架"——场景分析（第一阶段）与业务对象建模（第二阶段）都在主题域内展开。业务场景（`prod_scenario`，见 2.3）归属某个主题域。一个聚合/实体归属一个主题域，一个主题域可包含多个聚合/实体与多个业务场景。

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `subject_id` | integer | PK | 主键，序列 `seq_prod_subject` |
| `row_uuid` | uuid | UN, NOT NULL | 全局行标识（UUID v4） |
| `product_id` | integer | NOT NULL | → `prod_product.product_id`（所属产品/子系统，逻辑关联） |
| `subject_code` | varchar(64) | UN, NOT NULL | 主题域编码（如 `SA_PURCHASE`、`SA_INVENTORY`） |
| `subject_name` | varchar(128) | NOT NULL | 主题域名称（采购、库存、销售…） |
| `description_txt` | text | | 主题域职责说明 |
| `sort_order` | integer | | 显示排序 |
| `create_by` | integer | NOT NULL | 创建人（app.user_id） |
| `create_ts` | timestamp | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 创建时间 |
| `update_by` | integer | NOT NULL | 最后修改人（app.user_id） |
| `update_ts` | timestamp | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 最后修改时间 |
| `delete_flag` | smallint | NOT NULL, DEFAULT 0 | 逻辑删除标志 |
| `version_cnt` | integer | NOT NULL, DEFAULT 0 | 乐观锁版本号 |

> **设计要点**：聚合根（`cdm_aggregate.subject_id`）、实体（`cdm_entity.subject_id`）与业务场景（`prod_scenario.subject_id`）均引用本表主键，一个聚合/实体/场景严格属于一个主题域。主题域是"业务语义分类"，与物理 Schema 解耦——本表属**建模域**（`ddd`），物理表名前缀（`cdm_`/`ldm_`/`pdm_`）区分建模模块（第一层与第五层共用 `prod_` 前缀，层次不以前缀表达）。权限分级由主题域 + **实体字段纳入清单**（`cdm_dsfield`，见 3.8）共同驱动：主题域决定业务语义归类，字段纳入清单决定该实体是否进入行级权限管辖（至少纳入一个字段才受控）。

### 2.3 prod_scenario — 业务场景定义（业务场景层）

> 定义**业务场景/用例**（Business Scenario / Use Case），归属某个主题域（`prod_subject`）。描述某个业务场景的触发条件、主流程、参与角色——是**两阶段建模的起点**：先按场景分析业务逻辑（子场景 → 子场景活动），再由场景识别业务对象（`cdm_aggregate_scenario`，见 3.13）进入数据建模。**业务规则：每个场景至少包含一个子场景**（`prod_subscenario`，见 2.4）。

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `scenario_id` | integer | PK | 主键，序列 `seq_prod_scenario` |
| `row_uuid` | uuid | UN, NOT NULL | 全局行标识（UUID v4） |
| `subject_id` | integer | NOT NULL | → `prod_subject.subject_id`（所属主题域，逻辑关联，见 2.2） |
| `scenario_code` | varchar(64) | UN, NOT NULL | 业务场景编码（如 `SC_PURCHASE_ORDER`） |
| `scenario_name` | varchar(128) | NOT NULL | 业务场景名称 |
| `prod_scenariotype_dict` | varchar(64) | | 场景类型（字典，如 `MAIN`/`SUB`、`CREATE`/`MODIFY`/`QUERY`/`APPROVE`）。`_dict` 字典引用 |
| `description_txt` | text | | 业务描述 |
| `precondition_txt` | text | | 前置条件 |
| `main_flow_txt` | text | | 主流程/步骤（文本或步骤清单） |
| `actor_txt` | text | | 参与角色（如"采购员/审批人"） |
| `sort_order` | integer | | 排序 |
| `create_by` | integer | NOT NULL | 创建人（app.user_id） |
| `create_ts` | timestamp | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 创建时间 |
| `update_by` | integer | NOT NULL | 最后修改人（app.user_id） |
| `update_ts` | timestamp | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 最后修改时间 |
| `delete_flag` | smallint | NOT NULL, DEFAULT 0 | 逻辑删除标志 |
| `version_cnt` | integer | NOT NULL, DEFAULT 0 | 乐观锁版本号 |

> **设计要点**：场景通过 `subject_id` 关联所属主题域（一个场景严格属于一个主题域），场景**至少包含一个子场景**。场景是建模主链路的一环：业务逻辑经子场景/业务活动（见 2.5）结构化分析，识别出的业务对象经 `cdm_aggregate_scenario`（见 3.13）关联到聚合，主追溯链为"产品 → 主题域 → 场景 → 业务对象（聚合）→ 实体"。

### 2.4 prod_subscenario — 子场景定义（业务场景层）

> 定义**子场景**（Sub-Scenario），归属某个业务场景（`prod_scenario`），是场景的细化步骤/子用例，其下的**业务活动**（`prod_activity`，见 2.5）结构化承载业务逻辑分析。**业务规则：每个场景至少包含一个子场景**（应用层/业务规则保证，不建物理外键强约束）。

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `sub_scenario_id` | integer | PK | 主键，序列 `seq_prod_subscenario` |
| `row_uuid` | uuid | UN, NOT NULL | 全局行标识（UUID v4） |
| `scenario_id` | integer | NOT NULL | → `prod_scenario.scenario_id`（所属父场景，见 2.3） |
| `sub_scenario_code` | varchar(64) | UN, NOT NULL | 子场景编码（如 `SC_PO_CREATE`、`SC_PO_APPROVE`） |
| `sub_scenario_name` | varchar(128) | NOT NULL | 子场景名称（如"创建订单"、"审批"） |
| `description_txt` | text | | 子场景描述 |
| `precondition_txt` | text | | 前置条件 |
| `flow_txt` | text | | 子场景步骤说明 |
| `actor_txt` | text | | 参与角色（如"采购员/审批人"） |
| `sort_order` | integer | | 排序 |
| `create_by` | integer | NOT NULL | 创建人（app.user_id） |
| `create_ts` | timestamp | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 创建时间 |
| `update_by` | integer | NOT NULL | 最后修改人（app.user_id） |
| `update_ts` | timestamp | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 最后修改时间 |
| `delete_flag` | smallint | NOT NULL, DEFAULT 0 | 逻辑删除标志 |
| `version_cnt` | integer | NOT NULL, DEFAULT 0 | 乐观锁版本号 |

> **设计要点**：子场景通过 `scenario_id` 归属父场景（一个子场景严格属于一个场景），用于"主题域 → 场景 → 子场景"的业务逻辑逐层细化；其下的子场景活动（见 2.5）记录操作/输入输出/规则/状态流转，是场景分析的核心产出与业务评审依据。

### 2.5 prod_activity — 子场景业务活动定义

> 定义子场景下的**业务活动/步骤**（Sub-Scenario Activity / Step），结构化承载"**先按场景分析业务逻辑**"的产出：每个活动的操作类型、业务逻辑、输入输出、业务规则与状态流转。业务活动是场景分析的核心载体——活动中提及的业务名词即**候选业务对象**，经评审落为 `cdm_aggregate_scenario`（见 3.13）关联，驱动后续数据建模。

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `activity_id` | integer | PK | 主键，序列 `seq_prod_activity` |
| `row_uuid` | uuid | UN, NOT NULL | 全局行标识（UUID v4） |
| `sub_scenario_id` | integer | NOT NULL | → `prod_subscenario.sub_scenario_id`（所属子场景，逻辑关联，见 2.4） |
| `activity_code` | varchar(64) | UN, NOT NULL | 业务活动编码（如 `ACT_PO_FILL`、`ACT_PO_SUBMIT`） |
| `activity_name` | varchar(128) | NOT NULL | 活动名称（如"填写订单"、"提交审批"） |
| `prod_activitytype_dict` | varchar(64) | NOT NULL | 活动类型（字典）：`CREATE`（创建）/`MODIFY`（修改）/`QUERY`（查询）/`DELETE`（删除）/`APPROVE`（审批）/`NOTIFY`（通知）/`CALC`（计算）。`_dict` 字典引用 |
| `operation_txt` | text | | 业务逻辑描述（做什么、怎么做——场景分析核心产出） |
| `input_txt` | text | | 输入说明（前置数据/触发输入） |
| `output_txt` | text | | 输出说明（结果/状态变化/产出数据） |
| `rule_txt` | text | | **业务规则**——本活动上的约束/推导/校验逻辑（自然语言）。**全模型唯一的业务规则描述载体**；模型层（`cdm_`）不设规则表，详见下方"业务规则的承载" |
| `prod_fromstate_dict` | varchar(64) | | 活动前业务对象状态（状态字典项，如 `DRAFT`） |
| `prod_tostate_dict` | varchar(64) | | 活动后业务对象状态（状态字典项，如 `SUBMITTED`） |
| `sort_order` | integer | | 执行顺序 |
| `create_by` | integer | NOT NULL | 创建人（app.user_id） |
| `create_ts` | timestamp | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 创建时间 |
| `update_by` | integer | NOT NULL | 最后修改人（app.user_id） |
| `update_ts` | timestamp | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 最后修改时间 |
| `delete_flag` | smallint | NOT NULL, DEFAULT 0 | 逻辑删除标志 |
| `version_cnt` | integer | NOT NULL, DEFAULT 0 | 乐观锁版本号 |

> **设计要点**：子场景活动挂在子场景下（`sub_scenario_id`），按 `sort_order` 排列表征执行次序；`operation_txt`/`rule_txt` 中的业务名词经领域评审识别为业务对象，落为 `cdm_aggregate_scenario` 关联（见 3.13）；`prod_fromstate_dict`/`prod_tostate_dict` 表达业务状态流转（取值为相关实体状态字段的字典项），支撑状态机配置与前端流程渲染。
>
> **业务规则的承载（全模型唯一入口）**：本模型中，**业务规则的自然语言描述只有一处入口——本表 `rule_txt`**，聚合内不变式与跨聚合协作规则皆在此描述，**模型层不设规则表**（`cdm_aggregate_rule`/`cdm_aggregation_rule` 已删除）。规则的**描述**与**生效**是两件事：
>
> | 规则的内容 | 写在哪 | 由什么保证生效 |
> |---|---|---|
> | 某业务步骤上的规矩（约束/推导/校验） | **本表 `rule_txt`**（自然语言，业务可读、可评审） | —（描述本身不执行） |
> | 字段级取值/取值范围/格式/长度 | `config_json.validationRules`（见 9.3） | 引擎读取执行 |
> | 结构约束（非空/唯一/`CHECK`） | `pdm_constraint`（见 5.6） | DDL |
> | 跨字段/跨步骤、需事务或领域知识的判定 | 业务服务 `prod_service`（见 2.8）/ 事件处理器 `prod_eventhandler`（见 2.7） | 后端代码 |
> | 审批链、状态流转 | 平台工作流 `wf_*` | 工作流引擎 |
> | 随客户/产品/场景而变的阈值与开关 | **业务策略**，由应用服务层参数承载（见 8.20） | 运行期配置 |
>
> **为什么不单设规则表**：规则一旦脱离它所描述的业务步骤而单独建表，便必然产生"第二份真相"——既不被运行时读取（真正的执行在上表右列），又随实现演进而持续失真，最终徒增维护成本且无人敢删。**与其维护一张永远对不齐的台账，不如让描述紧贴它所属的业务步骤、让实现紧贴它的执行载体。**
>
> **追溯路径**：「活动 → 子场景 → 场景 → `cdm_aggregate_scenario`（见 3.13）→ 聚合」。事件（见 2.6）与业务服务（见 2.8）同样锚在场景/活动上，**经此路径而非直连聚合**到达业务对象。要回答"某个聚合上有哪些规则"，由 `cdm_aggregate_scenario` 反查其场景的活动再取 `rule_txt` 即可——**不需要独立的规则表建立第二份关联**。
>
> **写法建议**：一条 `rule_txt` 只写一条可验收的规矩；**把数值与开关抽成策略**——不写"金额超过 10000 需二级审批"，改写"金额超过审批起点金额需二级审批"，阈值交由业务策略参数承载。这样规则文本可跨客户复用，差异只落在参数。


### 2.6 prod_event — 业务事件定义（业务场景层）

> **业务事件（Business Event）**：记录领域中已发生的、有业务意义的事实（如"订单已创建"、"库存已扣减"），是**场景分析（事件风暴）产出的业务行为清单**——业务活动（见 2.5）改变业务状态时发出的信号。业务事件是**跨业务对象协作与最终一致性**的信号载体：事件由订阅方（`prod_eventhandler`，见 2.7）消费；应用层的订阅编排由 `prod_eventsubscription`（见 6.8）承接。对应 DDD 战术模式中的 Domain Event。
>
> **与聚合脱钩（重要）**：本表**不关联聚合**（原 `aggregate_id` 已删除）。事件回答"业务上发生了什么"，属于**业务行为**；聚合回答"数据如何组织"，属于**业务对象**——二者的衔接点在 `cdm_aggregate_scenario`（见 3.13）："该场景下有哪些业务对象参与"由那里登记，反过来也就回答了"该场景的事件牵涉哪些聚合"。若在此另设 `aggregate_id`，同一份归属要在场景链路与事件行上各写一遍，随任一侧调整而失真——这正是本模型连续删除冗余关联的一贯判据。**事件只锚场景，不发往数据结构**。
>
> **层级说明**：本表回答"业务上发生了什么"，**不绑定实现代码**——运行时的消费编排与执行分别由产品层（6.8）与应用系统层（8.3）承接。三张业务行为表（2.6～2.8）之所以放在场景层而非概念层，判据与规则表一致：**字段皆为 `*_txt` 业务描述、无代码锚点、描述的是业务行为而非数据结构**，放在概念层既不被运行时消费，又会与实际执行脱节。

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `event_id` | integer | PK | 主键，序列 `seq_prod_event` |
| `row_uuid` | uuid | UN, NOT NULL | 全局行标识（UUID v4） |
| `event_code` | varchar(64) | UN, NOT NULL | 事件编码（如 `ORDER_CREATED`、`STOCK_DEDUCTED`） |
| `event_name` | varchar(128) | NOT NULL | 事件名称 |
| `scenario_id` | integer | NOT NULL | → `prod_scenario.scenario_id`（**所属业务场景**，逻辑关联，见 2.3） |
| `activity_id` | integer | | → `prod_activity.activity_id`（**发出该事件的业务活动**，逻辑关联，可选，见 2.5） |
| `subject_id` | integer | NOT NULL | → `prod_subject.subject_id`（所属主题域，逻辑关联，见 2.2） |
| `prod_eventtype_dict` | varchar(64) | NOT NULL | 事件类型（字典）：`DOMAIN`（业务事件）/`INTEGRATION`（集成事件）/`APPLICATION`（应用事件）。`_dict` 字典引用 |
| `payload_txt` | text | | 事件载荷描述（携带的数据/字段说明，建模层只作描述，不落具体 JSON） |
| `occurrence_rule_txt` | text | | 触发规则（什么业务操作触发该事件） |
| `description_txt` | text | | 事件语义描述 |
| `sort_order` | integer | | 排序 |
| `create_by` | integer | NOT NULL | 创建人（app.user_id） |
| `create_ts` | timestamp | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 创建时间 |
| `update_by` | integer | NOT NULL | 最后修改人（app.user_id） |
| `update_ts` | timestamp | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 最后修改时间 |
| `delete_flag` | smallint | NOT NULL, DEFAULT 0 | 逻辑删除标志 |
| `version_cnt` | integer | NOT NULL, DEFAULT 0 | 乐观锁版本号 |

> **设计要点**：业务事件用于**业务对象之间的解耦**——某业务对象的状态变化以事件形式发布，不直接调用其他业务对象；订阅方通过事件处理器（`prod_eventhandler`，见 2.7）响应。事件锚定**业务场景**（`scenario_id`，见 2.3）并可精确到**发出它的业务活动**（`activity_id`，见 2.5），由此得完整追溯链"活动 → 子场景 → 场景 → 该场景参与的聚合（`cdm_aggregate_scenario`，见 3.13）"——**"事件由哪个聚合发出"是这条链的推导结果，不是需要登记的字段**。跨聚合协作规则仍描述在场景层活动上（`prod_activity.rule_txt`，见 2.5）——本表只登记"信号是什么"，不重复描述"如何协作"。
>
> - `scenario_id` **必填**：事件风暴是在具体场景里做的，脱离场景的事件没有评审主体；一次可由多个场景关心的事件，登记在其"产生它的场景"上，消费侧由处理器（见 2.7）声明。
> - `activity_id` **可选**：多数场景建议填——它能精确回答"哪个业务步骤导致该事实"（如"提交订单"活动发出 `ORDER_SUBMITTED`），使事件可反向定位到业务步骤；跨多个活动的通用事件留空即可。
> - 派生追溯：要回答"某聚合上会产生哪些事件"，由 `cdm_aggregate_scenario` 取该聚合的场景，再取这些场景下的事件——**不设 `aggregate_id` 这条捷径**。`prod_service` 同理，只挂 `scenario_id`。

### 2.7 prod_eventhandler — 事件处理器定义（业务场景层）

> **事件处理器（Event Handler）**：定义业务事件（`prod_event`，见 2.6）被哪个场景/服务消费。一个事件可被多个处理器订阅，实现"发布-订阅"解耦。对应 DDD 战术模式中的 Event Handler / Event Listener。

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `handler_id` | integer | PK | 主键，序列 `seq_prod_eventhandler` |
| `row_uuid` | uuid | UN, NOT NULL | 全局行标识（UUID v4） |
| `event_id` | integer | NOT NULL | → `prod_event.event_id`（被订阅事件，逻辑关联，见 2.6） |
| `handler_name` | varchar(128) | NOT NULL | 处理器名称 |
| `prod_handlertype_dict` | varchar(64) | NOT NULL | 处理类型（字典）：`SYNC`（同步）/`ASYNC`（异步）/`SAGA`（编排）。`_dict` 字典引用 |
| `consumer_scenario_id` | integer | | → `prod_scenario.scenario_id`（**消费方业务场景**，逻辑关联，可选，见 2.3） |
| `consumer_service_id` | integer | | → `prod_service.service_id`（消费方业务服务，逻辑关联，可选，见 2.8） |
| `process_logic_txt` | text | | 处理逻辑描述 |
| `sort_order` | integer | | 排序 |
| `create_by` | integer | NOT NULL | 创建人（app.user_id） |
| `create_ts` | timestamp | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 创建时间 |
| `update_by` | integer | NOT NULL | 最后修改人（app.user_id） |
| `update_ts` | timestamp | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 最后修改时间 |
| `delete_flag` | smallint | NOT NULL, DEFAULT 0 | 逻辑删除标志 |
| `version_cnt` | integer | NOT NULL, DEFAULT 0 | 乐观锁版本号 |

> **设计要点**：处理器关联消费方业务场景（`consumer_scenario_id`，见 2.3）或业务服务（`consumer_service_id`，见 2.8），二者至少其一——**消费侧同样不与聚合直连**（原 `consumer_aggregate_id` 已删除）："履约场景关心订单已创建"是场景级语义，落到具体聚合属于实现决策，由该场景的 `cdm_aggregate_scenario`（见 3.13）推导。异步/编排处理器支撑**最终一致性**——与活动上描述的跨聚合协作规则（见 2.5）配合实现 SAGA/发布-订阅等集成模式。与产品层 `prod_eventsubscription`（见 6.8）的边界：本表声明"谁关心该事件"（语义），订阅表声明"事件如何驱动能力端点"（执行），二者经 `event_id` 与 `api_id` 关联。

### 2.8 prod_service — 业务服务定义（业务场景层）

> **业务服务（Business Service）**：承载**跨聚合、无自然归属**的业务行为——该行为不属于单个聚合/实体，需要协调多个聚合完成（如"下单并扣减库存"、"计算客户信用额度"）。业务服务是无状态业务操作的**描述**，只回答"做什么、编排谁"，**不绑定实现代码**——实现由应用服务层（后端代码）承担。对应 DDD 战术模式中的 Domain Service。

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `service_id` | integer | PK | 主键，序列 `seq_prod_service` |

| `service_code` | varchar(64) | UN, NOT NULL | 服务编码（如 `PLACE_ORDER_SERVICE`） |
| `service_name` | varchar(128) | NOT NULL | 服务名称（如"下单服务"） |
| `product_id` | integer | NOT NULL | → `prod_product.product_id`（所属产品/子系统，逻辑关联，见 2.1） |
| `subject_id` | integer | NOT NULL | → `prod_subject.subject_id`（所属主题域，逻辑关联，见 2.2） |
| `scenario_id` | integer | | → `prod_scenario.scenario_id`（支撑的业务场景，逻辑关联，可选，见 2.3） |
| `service_logic_txt` | text | | 服务逻辑描述（编排哪些聚合、执行业务规则） |
| `prod_servicetype_dict` | varchar(64) | | 服务类型（字典）：`USE_CASE`（用例服务）/`COMPUTATION`（计算服务）/`POLICY`（策略服务）。`_dict` 字典引用 |
| `description_txt` | text | | 服务职责描述 |
| `sort_order` | integer | | 排序 |
| `create_by` | integer | NOT NULL | 创建人（app.user_id） |
| `create_ts` | timestamp | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 创建时间 |
| `update_by` | integer | NOT NULL | 最后修改人（app.user_id） |
| `update_ts` | timestamp | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 最后修改时间 |
| `delete_flag` | smallint | NOT NULL, DEFAULT 0 | 逻辑删除标志 |
| `version_cnt` | integer | NOT NULL, DEFAULT 0 | 乐观锁版本号 |

> **设计要点**：业务服务与业务对象分工——业务对象内聚自身规则，业务服务编排跨业务对象流程（服务本身只挂 `scenario_id`，与聚合不直连）；与 `prod_event`（发布事件，见 2.6）和 `prod_eventhandler`（消费事件，见 2.7）配合实现复杂用例。识别信号：某行为"不属于任何单个业务对象"或"涉及多个业务对象协作"时登记为业务服务。与 2.5 的分工：活动描述**场景内的步骤与规则**（业务可读、可评审），业务服务登记**跨聚合的行为归属**（开发实现的锚点）。
