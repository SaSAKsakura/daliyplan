# 配置中心操作手册2.5

**配置中心操作手册**

## 配置流程

使用配置中心能够快速生成页面，加速开发效率，统一页面风格。使用配置中心时，在选择项目后，首先需要进行功能定义，在功能中关联数据表，新增操作列表，配置类信息，新增容器和容器的子控件。在同步配置后根据定义的功能来配置菜单，最后在角色定义中给对应的角色分配操作权限。以上为一个完整的配置流程。

功能定义功能说明


|      |                                                                                                              |
| ---- | ------------------------------------------------------------------------------------------------------------ |
| 名称   | 说明                                                                                                           |
| 功能代码 | 功能点的名称代码                                                                                                     |
| 模块代码 | 表示功能点属于哪个模块。一个系统通常由多个模块组成                                                                                    |
| 资源代码 | 资源码（RSCode）对应资源值（RSValue），用于展示成前端固定的文本（UcLabel和UcTab的内容、UcBouldField控件的表头）。也可以用资源代码来实现消息框的消息内容提醒。资源代码与数据库无关。 |
| 描述   | 对功能点的描述                                                                                                      |
| 容器列表 | 定义容器，容器中可以添加子控件                                                                                              |
| 类信息  | 定义功能点的一些基本信息，如数据库信息和搜索框信息                                                                                    |
| 关联表  | 定义该功能点关联的表                                                                                                   |
| 操作列表 | 定义该功能中可用的操作                                                                                                  |

## 数据资源控制

在**菜单定义**和**角色定义**中，可以为不同的角色配置不同的操作权限，如查看，编辑，新增，删除等。除此之外，还可以通过配置**数据资源**来控制对同一菜单下能访问的数据的范围的限制，使不同角色在访问同一菜单时访问到的数据的范围不同。实现效果如：员工信息菜单中，A角色可查看所有的用户，B角色只能查看自己的数据。

## 一览表容器UcGridviewContainer

在第一章中，以一览表的配置为例，介绍了一个完整的配置流程。本章节将详细介绍一览表容器的功能和属性。

展示风格

一览表有两种展示风格：1.带详情页的一览表 2.单行编辑一览表

容器名称中包含DJListView时，在页面中渲染成带详情页的一览表Z

其他情况下，渲染成单行编辑一览表

属性

CtnrUID（自动生成）：与容器创建时填写的ctnr\_uid相同，是容器的名称，此ID不是真正意义上的ID，此ID**并非唯一**。此属性通常填DJListView或者SetUpGrid。

![](markune-asset://03cd16bd708a1519d5fc578a2f9fcc491f5a864220f6835d290f89ff2e73857f)

FnCode（自动生成）：与功能创建时填写的功能代码相同。

![](markune-asset://5d8d58a0b4cfbe1077ad21135d80b63507d2c0d954d49738607820474139424f)

FnParameter（自动生成）：与容器创建时填写的功能参数相同。

![](markune-asset://9eb762f58992fa83db38a208713625258023b16dcce0f7d1ef6020c2bbe1a9ab)

根据CtnrUID、FnCode、FnParameter三个属性确定一览表的容器，在一个功能中，容器的CtnrUID可以重复，但是在添加容器时以上三个属性的组合必须是**唯一**的。

\*DataSourceDBActionCtnrUID：获取数据资源的容器 (在通过配置无法实现取值的情况下,可以自定义返回数据)，同时需要配置好相应的子控件占位。

存储过程中需要传入pRows和pPage，返回totalCount。见附件:sample.sql

![](markune-asset://ad93e0b07f8d316da560e7ce36eecdf32e4e5e9cce036d6fde68659de3ee55c8)

ID（自动生成）：此ID具有**唯一性**，但使用场景较少，有C59399\_datakeys的用法，在使用存储过程时，可以以此作入参，作为筛选条件。

![](markune-asset://eeacfcd26e89314388af4785b2081ce0a2a27f68c1c6b20701339d3aaadec236)

HideOps：隐藏的操作列表，虽然在菜单和权限中有管理权限的功能，但在一个功能中定义的容器数量较多而权限各自不同时，则需要更细的权限管理，因此此处添加了隐藏操作列表的属性作为权限管理的补充。

#### 在默认模式下动态展示初始值

文本框、日期控件等需要在默认模式下展示动态初始值时，配置控件的`SetParameterValueAction`属性，值为负责取值的`SqlDBAction`或`StoredProcDBAction`容器名称。

若初始值固定，使用`DefaultValue`；若参数列表中已经存在目标值，使用`DefaultValueFromParameterName`。只有需要通过数据库动作动态取值时才使用`SetParameterValueAction`。

### 自定义查找类型

存在部分场景：查找条件的字段不在业务表中。如一个包含工作流的场景，根据流程状态查找单据。此时产生一个问题，单据的流程状态不直接存在单据的业务表中，而是存在工作流相关的表中。此时不通过自定义查找条件，无法实现查询效果。

通过配置SearchFormat实现：自定义查询语句的格式, 如{0}={1}, {0}:字段名(含别名),{1}:值

示例：wf.GetInstanceStepID(T.row\_guid) = {1}

#### 查找条件变化后自动查询

需要在查找条件发生变化后立即刷新查询结果时，在该查找控件的`AutoPostBackAction`属性中配置：

```json
{"function":[{"event":"onchange","refFunction":"searchForm"}]}
```

`onchange`表示控件值变化时触发，`searchForm`是本节列出的查找函数。保存并同步当前功能后，修改查找条件，确认目标列表或看板无需点击查询按钮即可刷新。

若配置后没有触发查询，依次检查：配置是否写在实际发生变化的控件上、JSON格式是否有效、目标容器是否已正确关联查找容器，以及当前功能是否已同步。

## 控件联动

控件联动的功能是在一个控件发生变化后，另一个控件随之一起做出变化。

控件联动的常用用法有设置必填/非必填，颜色和是否隐藏等。

通过在**AutoPostBackAction**属性中配置json格式的文本实现。

**AutoPostBackAction**属性用法1：控件联动

规则匹配上后执行的指定规则，"regulation":

CtnrID:容器id

ControlID:需要控制目标控件的ID

OnInit: 是否需要初始化的时候执行，默认初始化时候不执行，当前控件有变化的时候执行

--Action:定制化行为，多个逗号隔开，前端定义一些全局的is函数，

--clearValue:清空值

SetValue:设置值，(一般在前一个控件的行里面就带出目标的值，把当前行数据的某个值赋值过去)

SetDataSource: 设置数据资源，前端固定调用sysloadontrolData接口，传入当前控件填(选中)的值,token,pValueset,容器ID,目标控件id,接口成功后获取目标容器的数据源，并替换原有的值

SetConfig:设置配置属性，重新绑定新的属性，例如设置必填或非必填,颜色，隐藏等

{

"ClientAction": \[{

"regex": "/test/", -- 正则表达式，填写匹配规则(前端根据控件的值，按规则指定规则匹配当前需要执行的Action,可以匹配输入长度或者其他情况)

"regulation": \[

{

"ContianerID":"C59851",

"ControlID": "C59851\_7",

"OnInit": true,

"Action": \[{

"ClearValue": \[\]

},

{

"SetValue": \[{

"value": "text"

}\]

},

{"SetDataSource":\[\]},

{

"SetConfig": \[{

"ClientClass": "red"

}, {

"disabled": "false"

}\]

}

\]

}

\]

}\],

}

#### 调用DBAction时必须同步配置容器

当`actionType`配置为`dbAction`时，必须同时配置`dbActionCtnrUid`，否则按钮没有可调用的目标容器。`dbActionCtnrUid`填写`UcPostContainer`的容器标识，格式为`FnCode.FnParameter.CtnrUID`，不要直接填写存储过程容器名称。

配置后保存并同步当前功能，再点击按钮验证接口是否实际发起。若按钮可点击但接口未调用，先核对`actionType`与`dbActionCtnrUid`是否成对配置，再检查功能代码、功能参数和容器标识是否与目标`UcPostContainer`一致。

1.4文件上传的原理

当**新增**一条数据时，系统会自动为该数据的row\_guid字段设置一串长度为36的一串序列。文件上传时，会保存所点开的行的数据的row\_guid。在文件上传完成后，往erow\_biz库的fs\_file表中插入一条数据，一览表中数据的row\_guid对应保存到fs\_file中的instance\_guid字段中。

那么如何实现获取一览表中某行数据中提交的文件列表和数量？在fs\_file表中若有几条数据的instance\_guid字段相同，那么说明fs\_file表中的这几条数据是在一览表中，是在同一行的明细界面提交的（row\_guid的唯一性）。可以用以下存储过程实现：

CREATE DEFINER=\`root\`@\`%\` PROCEDURE \`GetFileList\`(IN row\_guid VARCHAR(36))

BEGIN

SELECT \*

FROM erow\_biz.fs\_file

WHERE erow\_biz.fs\_file.instance\_guid = row\_guid;

END

其中 SELECT \* 部分可以根据需要的字段进行修改，或者用COUNT()函数来实现获取文件数量。

## 工作流容器UcWorkflow

工作流为一个审批的流程，每一流程有指定的审批人和操作。

### 表结构规范

——若启用工作流，表字段必须包含 applicant\_user\_id（默认值为sys.userid，取当前登陆人。IsAllowUpdate属性配置为false，不允许更新）和applicant\_team\_id 字段，并指定 int 类型。无需配置submit\_flag字段。

### 基本配置步骤

applicant\_user\_id（申请人id）在整个工作流起到的作用？

记录该工作流是谁提交的，

判断applicant\_user\_id和当前登录人的id是否相同，判断是否返回重新修改权限，申请人有重新修改权限，其他人无重新修改权限。

applicant\_team\_id（申请人所在团队id）有什么作用？

记录提交人所在的团队的id

row\_guid的作用？

根据单据的row\_guid关联工作流相关表中的instance\_guid。可将单据的row\_guid作为一些工作流相关函数的入参，查询工作流的信息，如当前步骤、单据状态等

## 动态列容器UcDynamicContainer

基本功能

在UcGridviewContainer容器中，若使用UcBoundField容器，只能实现固定的列数的一览表。若需要实现动态列的效果，需要引入动态列容器UcDynamicFieldGroup。在动态列容器的配置中，容器的配置是容易的，重点是获获取数据源

以下操作均需在一览表已经实现的基础上完成。

1. 新增UcDynamicFieldGroup容器

需要为UcDynamicFieldGroup容器配置固定的三个属性，一个或多个子控件。


|                  |                                                                                                                                                                   |                                                   |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| 属性名              | 值类型                                                                                                                                                               | 属性描述                                              |
| HeaderDataSource | {UID:datasourceContainerUID, TextField:fieldname,TypeField:fieldname,ExportTextField:fieldname,ExportValueKeyField:fieldname,KeyField:fieldname}                  | 表头数据源，为某一DataSourceContainer的UID；                 |
| DetailDataSource | {UID:datasourceContainerUID, HeaderKeyField:fieldname,ExportTextField:fieldname,ExportValueKeyField:fieldname,RowKeyField:fieldname,ShowStyleFieldName:fieldname} | 明细数据源，数据值为json格式，UID表示使用的数据源控件，HeadKeyField：表示对应的 |
| DataField        |                                                                                                                                                                   | 对应主表每一行的关联数据键值                                    |
| HTMLEncode       | true或者false                                                                                                                                                       | 支持表头HTML解码，实现换行等效果                                |


HeaderDataSource和DetailDataSource均使用Json格式来配置数据源的属性，分别表示表头和单元格的数据源的配置。若想获取数据源，则需要在容器列表中新增存储过程容器StoredProcDBAction和UcPostContainer。

HeaderDataSource属性：

1. UID：填写获取数据的UcPostContainer容器的ctnr\_uid。其余三个字段TextField、TypeField、KeyField均填写从该容器中获取到的数据字段名。
2. TextField：表头的文本内容
3. TypeField：表示列中子控件的类型，数据源中，该字段的值有多少种，就需要在添加多少个对应的子控件。
4. ExportValueKeyField:fieldname：表示导出为Excel时，在单元格中显示的文字
5. KeyField：表头和单元格关联的字段，与DetailDataSource中的HeaderKeyField字段对应。

DetailDataSource属性：

1. UID：与HeaderDataSource的UID类似，不同之处在于数据源需要获取的字段的不同。
2. RowKeyField：填写的数据源所在表的主键字段名
3. ShowStyleFieldName：单元格的样式的数据字段名。
4. HeaderKeyField：表头和单元格关联的字段，与HeaderDataSource中的KeyField字段对应。
5. ValueKeyField：单元格的数据的值的数据字段名

DataField属性：明细数据源对应主数据源的字段名。

6.联动树结构

展示的点位信息根据树结点过滤。

1.布局

使用Layout容器，左右别分引用树容器和地图容器。

而不是配置树结构右侧关联的容器为地图容器。原因：每次切换节点时重新加载右侧容器的配置，导致地图会重新渲染，体验上不流畅。

2.要实现树容器和地图组件的联动，可以通过配置树结构的TargetContainerActions 属性处理

**配置示例如**下  
  {

      "leafNodeClick": {

      "action":"centerAndopenTargetLayer",

      "targetCtnrUID":"MapContainer",

      "paramsMap":{"node\_key":"keyField"}

      }

      },

其中leafNodeClick ,代表是叶子节点点击，

action 中的centerAndopenTargetLayer是地图组件内的内置方法，通过该方法会将当前树节点居中

targetCtnrUID是 地图容器的CtnrUID,通过CtnrUID可以知道需要联动的容器

paramsMap 是为了统一action中对应方法的入参，其中node\_key 是树节点的字段名，keyField 是action 对应方法所需的参数名
